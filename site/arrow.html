docs / arrow & arrowref

Arrow in shared memory

How a columnar table becomes a 24-byte descriptor: shm-arrow writes an Arrow RecordBatch once into shared-memory chunks and rebuilds it zero-copy on the other side. ArrowRef is the product that wants exactly this contract — descriptors on the wire, payload on the data plane.

the one idea

Write once, move a descriptor

Everything in the substrate follows one rule: payloads are written once; everything downstream moves the 24-byte ChunkDesc. shm-arrow is that rule applied to Apache Arrow.

RecordBatchwriter process
write_batch ▶one copy in
chunk(s) in shmimmutable once published
24 B ChunkDesc ▶ring / task / cell
RecordBatchreader process, zero copy
  • One copy in, zero after. The writer serializes buffers into a loaned chunk. The reader builds Arrow buffers whose pointers land inside the mapped segment.
  • Reconstruct cost is flat in row count. 208–250 ns whether the table holds 1 000 or 1 000 000 rows (benchmarks).
  • The write is memcpy-bound. ~80 GB/s on the dev machine is memory bandwidth, and the docs do not call it “ingestion”.

ABI · SHMARBT2 · format 2

On-chunk layout

A written batch occupies one or more loaned chunks. The first (primary) chunk starts with a header and two flat tables; payload buffers follow, each 64-byte aligned (Arrow's required alignment).

primary chunk (chunk_index 0)
┌──────────────────────────────────────────────────────────────┐
│ BatchHeader                   32 B at offset 0               │
│ NodeEntry   × node_count      24 B each                      │
│ BufferEntry × buffer_count    12 B each                      │
│ <pad to 64>                                                  │
│ buffer bytes   (64-byte aligned, packed until chunk fills)   │
└──────────────────────────────────────────────────────────────┘
continuation chunks (chunk_index 1..)
┌──────────────────────────────────────────────────────────────┐
│ buffer bytes   (64-byte aligned from chunk offset 0)         │
└──────────────────────────────────────────────────────────────┘

BatchHeader — 32 bytes

fieldtypemeaning
magicu64b"SHMARBT2" little-endian. A v0.2 SHMARBT1 chunk is rejected here.

schema_idu32Interned schema id; mirrors ChunkDesc.schema_id.

node_countu32Length of the flattened pre-order node table.

chunk_countu32Chunks the batch spans (≥ 1).

NodeEntry — 24 bytes

One per node in a pre-order depth-first walk of each column's ArrayData tree. The DataType is not stored: the reader walks the schema in lockstep, exactly as Arrow IPC does. Only runtime facts are recorded.

fieldtypemeaning
lenu32Logical array length.
null_countu32Number of nulls.
has_validityu321 if a validity bitmap precedes the data buffers.
data_buffersu32Non-validity buffers: 1 for a primitive, 2 for Utf8 (offsets + values), 1 for List offsets, 0 for Struct.
child_countu32Child nodes that follow: field count for Struct, 1 for List.
_padu32Reserved, zero.

BufferEntry — 12 bytes

fieldtypemeaning
chunk_indexu32Which chunk of the batch holds the buffer (0 = primary).
offsetu32Byte offset from the start of that chunk, 64-byte aligned.
lenu32Byte length.

Absolute address of a buffer: segment_base + chunks[chunk_index].offset + offset, valid for len bytes.

Multi-chunk rule. When the next buffer would overflow the chunk, a continuation chunk opens. Every individual buffer stays contiguous inside one chunk — a buffer never straddles a boundary, because that would break zero-copy. A single buffer larger than the pool's max chunk size is rejected with Error::Unsupported.

The records are plain #[repr(C)] PODs placed by hand and never mutated after the chunk is published, so they carry no atomics. Sizes and alignments are pinned with compile-time asserts (32/8, 24/4, 12/4).

shm_arrow::write

Write path

let registry = SchemaRegistry::new();
let alloc    = PoolAllocator::new(&pool, &segment);

// common case: the batch fits one chunk
let desc: ChunkDesc = write_batch(&alloc, &registry, &batch)?;

// large or nested: ordered list, chunks[0] is the primary
let chunks: Vec<ChunkDesc> = write_batch_chunks(&alloc, &registry, &batch)?;
  1. Intern the batch's schema to get schema_id.
  2. Plan: flatten each column's array tree into nodes and buffers.
  3. Pack buffers 64-byte aligned against alloc.max_chunk_size(), opening continuation chunks as needed.
  4. Allocate and fill. If allocation fails part-way, every still-FREE chunk is returned (ChunkAllocator::free), so a failed multi-chunk write leaks nothing.
  • write_batch is a wrapper: if the batch needs several chunks it frees them and returns Error::ChunkTooSmall. Use write_batch_chunks for those.
  • Sliced arrays are normalized. Any array with a non-zero offset, at any nesting depth, is compacted (via arrow-select's concat) so the stored representation has offset 0. A reader never sees a non-zero offset.
shm_arrow::read

Read path

let pin   = Arc::new(PinGuard::new(segment.clone()));
let batch = read_batch(pin, &ctrl, &desc, &registry)?;   // buffers point into shm

// multi-chunk: ctrls is parallel to chunks
let batch = read_batch_chunks(pin, &chunks, &ctrls, &registry)?;

Each Arrow Buffer is built with Buffer::from_custom_allocation over a pointer into the segment and holds a clone of the owner as keep-alive. That is why a batch can outlive the call that produced it, but never the pin it views.

Validation order

Cheap, fail-closed, in this order:

  1. ctrl.validate(desc) for every chunk — generation must match, else shm_core::Error::StaleDescriptor.
  2. Header magic and format, else BadMagic.
  3. Header schema_id equals chunks[0].schema_id, else SchemaMismatch.
  4. chunk_count == chunks.len() and every buffer entry lies inside its chunk, else Layout.
  5. Registry lookup, else UnknownSchema.
The caller's half of the contract. The reader must hold every chunk in PUBLISHED state with a shared pin for as long as owner lives. Given that, the mapped bytes are immutable and reading them is sound. PinGuard is the canonical owner (it keeps the Arc<Segment> mapped); a full runtime also holds the ChunkCtrl refcount so the chunk cannot be recycled under the reader.
schema.rs · ADR-0003 item E

Schema interning

A schema_id is a u32 carried in both the ChunkDesc and the batch header. The wire form of a schema is its canonical Arrow-IPC schema message (serialize_schema / deserialize_schema), a pure function of the schema and byte-identical across processes on the same Arrow version.

  • Content hash. schema_content_hash is FNV-1a (64-bit) over those bytes. It is process-independent and is the key both the registry and the coordinator intern on.
  • Local vs coordinator ids. intern mints an id locally; insert(id, schema) installs one learned from the coordinator. Keyed on the content hash, both resolve to the same slot for the same schema.
  • Seeding. SchemaRegistry::with_schemas(&[..]) gives a writer and reader identical ids without a coordinator round trip.
  • Lookups. id_for(&schema) and resolve(id) are read-only; resolve of an id never installed yields None, surfaced as UnknownSchema on read.
Open edge. The registry is in-process. A reader in another process must receive the schema from the coordinator before its first read — an unresolved id is an explicit error, never a guess.

ArrowRef

What ArrowRef is

ArrowRef (the query-cache codebase) is a descriptor-first retained-execution cache. Queue and control messages never carry large payloads: Arrow or Parquet data is retained once, referenced by descriptors, and moved only by explicit data-plane fetches. Its task fabric is that invariant applied to work — submit task → worker executes → retained output ref → ack.

That is the same invariant shm-arrow implements at the byte level, which is why shm-actors is a candidate substrate for it. shm-actors stays clean-room: it has no dependency on ArrowRef, and the integration work lives in a separate spike crate and ADRs.

crates/shm-arrowref-spike · ADR-0005

The task-fabric spike

A runnable example, not a shipped library and not a port. It proves one surface end to end against a small hand-written mock of ArrowRef's task contract.

  1. A requester retains an Arrow input once in shared memory and submits only its 24-byte descriptor to a TaskQueue.
  2. A worker (a thread standing in for a process; the handles are the ones a cross-process actor gets) claims it exactly once and reads the input zero-copy.
  3. It computes a derived batch and retains it as a new Artifact version, then completes the task with a 24-byte result descriptor naming that version.
  4. The requester waits, reads the output zero-copy, and acks: the retained input is released and reclaimed.

The queue never carries a payload. Control messages are 24 bytes each; the Arrow data is written once and thereafter only referenced.

Where it stops. The spike surfaced concrete API gaps (durable task WAL, lifecycle-tied leases, evict-current) recorded in ADR-0005. Run it from the workspace root: managed-build cargo run -p shm-arrowref-spike.
direction

Re-front, not rebuild

The target for ArrowRef is five planes: a thin translator front (subdomain → tenant → typed descriptor envelope); the dispatch fabric (shm-actors, the spine of that plane only); a node/control plane with the tenancy catalog and a WAL; a per-tenant worker cluster with fd-granted segments; and the existing cross-host cluster.

  • Boundary rule: descriptors never cross a host; bytes do. shm-actors is same-host only.
  • Strangler order: tenancy catalog first, then the keyed store and typed-ref envelope, then the Tasks wedge behind a feature flag, topics next, the DuckDB worker path last.
  • Isolation comes from per-tenant segments granted by file descriptor, not from a software check.

Full detail: docs/ARROWREF-TARGET-ARCHITECTURE.md and docs/ARROWREF-INTERFACE-COLLAPSED.md in the repository.

practice

Rules of thumb

  • Never ship the batch, ship the descriptor. If a message grows with row count, the design is wrong.
  • Keep the pin as long as the batch. A RecordBatch from read_batch is a view; its owner must stay alive and the chunk must stay PUBLISHED.
  • Treat StaleDescriptor as a normal outcome. It means the data was reclaimed, which is the designed behavior for a late reader.
  • Seed or resolve schemas before reading. UnknownSchema is an ordering bug, not a data bug.
  • Size arenas with serialized_len, and use write_batch_chunks for anything that may exceed one chunk.
  • Check the type list first. Dictionary-encoded columns must be materialized before they can be written.
