The actor model

What an actor is in Holon, what a message is, and the exact API you write against — holon-core for the ABI, holon-actor for the runtime. Every signature on this page is the one in the crates today (ADR-0015, ADR-0017); the working code is crates/holon-demo.

The model

Two laws

Actors own no state. Memory nodes own no code. Everything else in this page falls out of those two sentences.

An actor is a handler, not a container

An actor struct holds addresses — a CellRef naming a shared table, a counter that is explicitly scratch. It never holds the data. A handler pins the exact cell version its message names, reads it zero-copy, and drops the pin when it returns. Kill the process: nothing of value dies with it.

A memory node is data, not a service

Cells, streams and artifacts are versioned Arrow bytes in shared memory with no attached behaviour. Any actor may read any version at full speed; no actor is the gatekeeper of one. That is what makes a worker pool interchangeable and a restart free.

Concretely: one process hosts any number of actors of any types, sharing one mailbox — the coordinator's shm-task queue — and the envelope's to field picks which handler runs. Several processes that spawn the same name form a pool: same ActorId, same queue, exactly-once claim decides who gets each message.

Where this page sits. The guide explains the substrate underneath — rings, cells, tasks, the borrow journal. This page is the layer you write against. Read Tasks and Versioned cells first if a term here is unfamiliar.

What a message is

A message is one chunk of the keyed store's shared pool: a 64-byte Envelope at offset 0, then the body inline at offset 64. The chunk travels as the task's 24-byte ChunkDesc — the data never moves, the descriptor does.

The envelope is a frozen ABI: #[repr(C, align(64))], exactly one cache line, magic-validated on decode, and designed to double as the frame header when a cross-host transport lands.

holon-core::Payload

Payloads: plain old data with a schema id

A message body is a POD struct. No pointers, no Drop, no padding — it is memcpy'd into shared memory and read by another process, so SharedPod is the contract and bytemuck proves it. Payload adds one thing: a SCHEMA_ID that the receiver dispatches on.

use holon_core::Payload;
use shm_core::SharedPod;

pub const PRICE_REQUEST_SCHEMA: u32 = 1001;

#[repr(C)]
#[derive(Clone, Copy, Debug, PartialEq, bytemuck::Pod, bytemuck::Zeroable)]
pub struct PriceRequest {
    pub tenor: f64,
    pub notional: f64,
    pub seq: u64,
}

// SAFETY: #[repr(C)], three 8-byte scalars, no padding, no pointers, no Drop.
unsafe impl SharedPod for PriceRequest {}
impl Payload for PriceRequest {
    const SCHEMA_ID: u32 = PRICE_REQUEST_SCHEMA;
}

Payload gives you as_bytes() and from_bytes() for free. Schema ids are yours to allocate and must be stable across processes — they are the wire contract. Bodies larger than 192 bytes do not ride inline; they go in a cell or an object and the message carries the reference.

holon-actor::Actor

The Actor trait

Two methods. accepts() lists the schema ids this actor handles — the runtime builds a sorted function-pointer table from it, so dispatch is a binary search with no dyn and no allocation on the message path. handle() runs one message at a time, which is why you never write a lock.

impl Actor for Pricer {
    fn accepts() -> &'static [u32] {
        &[PRICE_REQUEST_SCHEMA]
    }

    fn handle(
        &mut self,
        _msg: &Envelope,
        body: &[u8],
        cx: &mut Cx<'_>,
    ) -> holon_core::Result<Reply> {
        let req   = PriceRequest::from_bytes(body)?;
        let curve = cx.pin(&self.curve)?;        // journaled: kill -9 safe
        let rate  = interpolate(&curve, req.tenor)
            .map_err(holon_core::Error::Handler)?;

        Reply::of(&PriceReply {
            px: price(rate, req.tenor, req.notional),
            curve_version: curve.version(),      // which edition answered
            incarnation:   self.incarnation,      // which process answered
            attempt:       cx.attempt(),          // 0 = first delivery
        })
    }
}

The struct behind it holds a CellRef — a key, not data — plus whatever process-local scratch you are willing to lose:

pub struct Pricer {
    curve: CellRef,      // CellRef::new(CURVE_KEY) — an address
    handled: u64,      // scratch; lost on restart, by design
    incarnation: u32,  // std::process::id()
}
The tell for a wrong actor. If restarting your actor would lose something a caller cares about, the state is in the wrong place. Move it into a cell and pin it per message — that is the whole trade this framework makes.
holon-actor::ActorSystem

Hosting actors

An ActorSystem owns a shm-runtime Node, hosts any number of actors, and runs one mailbox loop. Register Arrow schemas before spawning; set the lease and the wait strategy; then run() until the stop flag flips.

let mut sys = ActorSystem::connect(&uds, PRICER_NAME)?;
sys.intern_schema(&curve_schema())?;
sys.set_lease(Duration::from_millis(500));  // DEFAULT_LEASE
sys.set_spin_budget(SpinBudget::from_micros(3));  // the default; 0 = park at once
sys.set_stop(stop.clone());                 // Arc<AtomicBool>

// Two actors, one mailbox: the envelope's `to` picks the host.
sys.spawn(PRICER_NAME, Pricer::new(kill_after, result))?;
sys.spawn(RISK_NAME,   Risk::new())?;

sys.run()?;

Head-of-line note: co-hosted actors share one mailbox, so a slow handler delays its neighbours. Per-actor mailboxes are not built — split into processes when isolation matters.

holon-actor::ActorRef

Calling an actor

A client attaches its own Node and opens an ActorRef per target. One node can carry several refs; they share the mailbox and differ only in to.

let mut node = Node::connect(uds, "client-0", Arc::new(SchemaRegistry::new()))?;
let mut pricer = ActorRef::new(&mut node, ActorId::named(PRICER_NAME))?;
let mut risk   = ActorRef::new(&mut node, ActorId::named(RISK_NAME))?;
pricer.set_spin(spin);

// fire and forget
pricer.tell(&evt)?;

// request / response, typed both ways
let rep: PriceReply = pricer.ask::<PriceRequest, PriceReply>(&req)?;

// zero-copy reply: read straight out of the reply chunk, release on drop
let guard = pricer.ask_ref(PriceRequest::SCHEMA_ID, req.as_bytes(), reply_cap)?;
let rep = guard.payload::<PriceReply>()?;

// pipelined: submit now, collect later
let mut pending = pricer.ask_start(PriceRequest::SCHEMA_ID, req.as_bytes())?;
while pricer.ask_poll(&mut pending)?.is_none() { /* do other work */ }

holon-actor::Cx

The handler context

Cx is everything a handler is allowed to do to the outside world. It is passed per message and borrows for exactly that message.

Tuning

The latency knob is a budget, not a switch

Both halves of an ask can wait: the worker for a message, the asker for its answer. Each waits the same way — busy-poll for a budget, then park on a doorbell and give the core back.

sys.set_spin_budget(SpinBudget::from_micros(3));   // the default
sys.set_spin_budget(SpinBudget::PARK_NOW);         // idle actor: give the core back at once
sys.set_spin_budget(SpinBudget::NEVER_PARK);       // hot path: keep the core, best tail

pricer.set_spin_budget(SpinBudget::from_micros(3));  // the asker's half, set independently

Why a budget beats a switch: a parked wake is a scheduler round trip — enqueue the waiter, IPI the target core, exit its idle state, resume a thread whose cache is now cold. That costs microseconds and has nothing to do with copying. A spinning round trip costs 1.2 µs. So a budget that covers one round trip lets the waiter see its own answer and skip the scheduler entirely; the queue only touches the notification machinery when it actually goes quiet.

Two things that surprise people. Spinning uses less total CPU — the same 50 000 asks cost 0.47–0.63 core-seconds parked and 0.15–0.20 spinning, because two hot cores for a fifth of the time beat one core waiting on the scheduler. And the cost is bounded and paid on the way to idle: an actor with nothing to do spins its budget once, parks, and costs nothing until the doorbell rings. The cores column above is the saturated worst case, not the resting cost.

Set it per actor, from the workload. The budget's job is to cover the gap between messages. A pricing actor taking a message every few microseconds should hold its core; a reconciliation actor that wakes twice a minute should hand it back on the first miss. ADR-0007 G1 · ADR-0015

Who owns which chunk

Both chunks in an ask are allocated by the asker. This is the single most counter-intuitive rule in the framework, and it came out of crash testing rather than design.

chunkallocated byheld howfreed by
request envelopethe askerbare descriptor (FREE)the handler process, after complete
reply chunkthe askerLOANED + journaledthe asker's ReplyRef guard, or the coordinator

Why the reply cannot ride the task slot's result word. A completed slot is reusable capacity the instant it completes — the very next submit from any client pops it off the LIFO free stack — so a concurrent requester's poll would see StaleHandle instead of its result. The reply therefore lives in memory the asker owns, named in the request as a LocalRef. A stale handle after a wait is provably terminal, so the asker falls back to reading its own chunk: kind Reply = answered, kind Err = the handler failed, still zeroed = never handled.

Why that chunk is loaned and journaled. The journal is what lets the coordinator reclaim it when the asker dies mid-ask; the loan is what makes the journal record mean anything, because reclamation dispatches on chunk state and does nothing for a FREE chunk. Loan first, then record. The loan also makes the generation live: a reclaim bumps it, so a handler re-reads the generation and compares it with Envelope::reply_gen before writing. A mismatch means the asker is definitively gone, and the task is failed rather than answered into a chunk that now belongs to someone else.

Why the request is freed only after complete. A requeued task still names that chunk, so the successor must read the same bytes. A handler whose complete returns Lost — its lease lapsed, the task was redelivered — leaves the request to the new owner and frees nothing.

Stated, not hidden. The request chunk of an ask whose task is never successfully claimed — retries exhausted, or no worker ever runs — is freed by nobody: one chunk per such ask. Closing it needs a coordinator-side sweep of the request descriptors of terminally-failed task slots, which is not built.
Semantics

The failure model

  • Delivery is at-least-once, and says so. A claim carries a lease; if the holder dies or stalls past it, the task is redelivered and cx.attempt() increments. Handlers that are not idempotent must key on corr themselves — the framework will not pretend the redelivery did not happen.
  • Failover is observable if you care, invisible if you don't. The demo's replies carry incarnation (which process) and attempt (how many deliveries) alongside curve_version (which edition of the data). Most callers ignore all three; the ones that must reconcile can.
  • A zombie cannot scribble on a live reply. Handlers time-fence their reply write, and the reply_gen epoch check catches the case where the asker died and its chunk was reclaimed and re-issued.
  • Recovery is mechanical and measured. kill -9 mid-message: the successor answers in the lease plus one tick — 508–542 ms at a 500 ms lease across eight runs — with one redelivery, zero messages lost, and a pool census that balances to the chunk.
  • Handler errors are messages too. Return Err from handle and the asker receives kind Err with the same corr; it is a reply, not a timeout.

Round trips, for calibration — Apple M4 Max, macOS, release, eight runs of holon-demo bench at 100 000 asks each: 9.0–10.0 µs p50 parked (p99 19.7–25.8), 1.2–1.4 µs spinning (p99 2.3–2.5). The envelope, pool, journaled pin and Arrow view together account for 1.3–2.6 µs parked and 0.6–1.0 µs spinning — everything else is the doorbell. Throughput is far noisier: 90–103 K asks/s at 1 client / 1 pricer, 134–220 K at 4 / 1, 120–174 K at 4 / 4 — four pricers do not beat one on this box, because the parked wake is the bottleneck, not the handler. In practice

Rules & traps

Bodies are POD or they are not bodies

#[repr(C)], no padding, no pointers, no Drop. SharedPod is unsafe for a reason: another process reads these bytes with no deserialization step to catch you.

192 bytes inline, then indirection

MAX_INLINE_BODY is 192. Bigger payloads belong in a cell or an object, referenced from the message. Do not grow the message; grow the memory node.

Size the reply before you ask

ask reserves DEFAULT_REPLY_BODY (192 B). A larger answer needs ask_start_sized / ask_ref with an explicit cap, and the handler should consult cx.max_reply().

Schema ids are a wire contract

They are yours to allocate, they must be stable across every process in the deployment, and accepts() must list exactly what the actor handles — an unlisted id is a routing error, not a silent drop.

Don't hold a pin across messages

Pinned borrows for the handler call. Holding one longer pins a version against reclamation and defeats the point; re-pin next message and read the newer edition.

Release ReplyRef promptly

It is a loaned, journaled chunk. Drop it (or call release()) as soon as you have what you need; leaking guards means leaking pool capacity until the coordinator reclaims.

The end-to-end reference is crates/holon-demo: two actors in one process, a client pool, a supervisor-injected kill -9, and a census that proves nothing leaked. Run it with cargo run -p holon-demo --release.
