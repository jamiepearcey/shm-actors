Benchmarks

Reproduce everything with cargo run -p shm-bench --release -- all — the suite prints its own hardware profile first. Numbers below: Apple M4 Max (14 cores), macOS, release builds, ≥ 2 runs per session.

Rules first

Method & wording

  • The timer floor is 41.7 ns. A reading of “min 0, p50 42, p99 42” is quantised, not measured — such results are reported “≤ 1 tick”, never as a constant.
  • Every suite runs at least twice. The machine drifts ±20–40 %; a single run once produced a phantom regression.
  • “Zero-copy” = no payload-size-proportional copy. View construction costs ~200–540 ns and is reported.
  • No invented comparisons. No baseline vs. iceoryx2 / Plasma / sockets has been run, so no “N× faster than X” appears anywhere.
  • macOS dev profile. The Linux futex/memfd fast paths compile clean cross-target but are unmeasured; no futex number is quoted.
  • Losing shapes ship in the suite. A change defaults on only after the row that punishes it exists.

A Window costs ~120–180 ns per kept chunk (member parse + two generation validations + one CAS + a 24 B descriptor write). Amortised over the policy that is 0.1–0.2 µs per commit — a seventh of an append — but the per-window tail is real and reported, not hidden in an average.

Crash & census

The census is the invariant that makes every other number trustworthy: after any hostile scenario — commit races, leaked-pin replay, kill -9 churn loops — free chunks minus baseline must equal the live data, to the chunk. It does, in 239 tests.

Reproduce

On your machine

cargo run -p shm-bench --release -- all        # full suite + hardware profile
cargo run -p shm-bench --release -- artifact   # pins, commits, windowed streams
cargo run -p shm-bench --release -- task       # claim scaling, drain shapes
cargo run -p holon-demo --release -- bench     # actor asks, throughput, crash row

Run everything twice. If your first run disagrees with your second by 30 %, that's the machine, not the code — it's why the method section exists.
